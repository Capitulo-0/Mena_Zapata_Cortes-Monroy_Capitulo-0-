DICTAMEN PRINCIPAL
Capítulo 0 tiene un frontend de demostración amplio y reutilizable y un backend funcional acotado a catálogo local, biblioteca, identidad Firebase verificada y health.
No existe hoy un flujo integrado Flutter -> Firebase -> API -> PostgreSQL.
El primer bloqueo es doble:
1) Flutter no incorpora Firebase Core/Auth, Google Sign-In ni un cliente de API.
2) El backend verifica identidad pero no aprovisiona al usuario nuevo: /api/me busca por firebase_uid y devuelve 404 cuando no existe vínculo.
Biblioteca/progreso son las áreas más cercanas a una conexión real: la API y las restricciones SQL ya existen.
Writer permite operar sobre obras/capítulos propios localmente; no constituye una plataforma de publicación multiusuario.
Social, moderación, mapas de dominio y los demás MUST HAVE carecen de persistencia y APIs completas.
Las carpetas preparadas con .gitkeep no representan funcionalidades implementadas.

F. FIREBASE, AUTENTICACIÓN Y SEGURIDAD
F.1 Flujo real hoy
Flutter: formularios -> simulateLogin -> cambio AppStage -> aplicación.
No obtiene ID token, no guarda sesión Firebase y no envía Bearer.
Backend: Authorization Bearer -> FirebaseBearerFilter -> FirebaseTokenVerifier -> FirebaseAdmin.verifyIdToken(token, checkRevoked) -> AuthenticatedFirebaseUser -> SecurityContext -> lookup users.firebase_uid.
La parte Spring está implementada; el tramo Flutter y el aprovisionamiento faltan.

F.2 Controles existentes
- Identidad siempre por UID verificado, no por userId/email enviados por cliente.
- Token crudo no queda retenido como credentials del Authentication.
- Encabezados duplicados/formato inválido se rechazan.
- GET públicos health/books omiten deliberadamente verificación del header.
- SecurityContext por request, sesión STATELESS, sin form login ni Basic.
- Sin cookies de autenticación; CSRF deshabilitado para API Bearer.
- /api/users está denegado, biblioteca legacy exige dueño.
- No hay auto-link por email. Evita que coincidencias de email vinculen cuentas indebidamente.
- ADC y FIREBASE_PROJECT_ID explícito, FirebaseApp/FirebaseAuth lazy.
- Emulador Firebase rechazado por inicialización productiva.
- Verificación de revocación por defecto true.
- Inválido/expirado/revocado: 401; acceso a biblioteca ajena: 403; fallo de inicialización/disponibilidad de identidad: 503.
- Respuestas sanitizadas, sin stacktrace ni rutas ADC.
- Falta CORS explícito para Flutter Web; una app Android nativa no está sujeta al mecanismo CORS del navegador.

F.3 Límites y riesgos reales
- La suite mockea FirebaseTokenVerifier o FirebaseAuth: no demuestra verificación de un JWT real de este proyecto.
- No se validó ADC local, permisos, project ID, conectividad o token real.
- /api/me con UID nuevo responde 404, confirmado por servicio y caso de test.
- users.email es obligatorio y único; el aprovisionamiento debe definir tokens sin email y conflictos con cuentas legacy.
- No hay rol de moderador/admin implementado ni control editorial del POST books.
- Las preferencias de privacidad Flutter no protegen datos en el servidor.
- Logout actual solo cambia UI. Con Auth real se necesita signOut y vaciado del estado por cuenta.
- SignOut cliente no revoca por sí solo todos los ID tokens emitidos; separar cierre local de revocación global según política.
- Health UP solo prueba DB accesible; puede convivir con Auth mal configurado.
- Listados no paginados y ausencia de límites operativos por dominio son deuda para crecimiento.

F.4 Lo necesario para PRIMER LOGIN REAL E2E
1. Incorporar/configurar Firebase Core/Auth y Google Sign-In en Flutter; inicializar Firebase y comprobar applicationId/configuración.
2. Reemplazar simulateLogin/Register por operaciones reales; Google debe producir credencial Firebase.
3. Observar sesión Firebase y restaurar navegación desde authStateChanges; recuperación de contraseña real.
4. Crear cliente de API con base URL por entorno, HTTPS, Bearer desde getIdToken y tratamiento de expiración/401/503.
5. Implementar aprovisionamiento idempotente basado únicamente en UID verificado. El cliente no elige UID ni dueño. Puede ser una operación explícita o un flujo de sincronización definido; no existe hoy.
6. Resolver email verificado, email ausente y colisión con cuenta legacy sin auto-link inseguro. La prueba actual protege precisamente que no se haga auto-link.
7. Disponer de ADC y project ID correctos en backend y DB migrada, mediante configuración fuera del repositorio.
8. Probar con cuenta nueva: login Firebase -> aprovisionamiento -> /api/me 200 -> biblioteca vacía -> añadir libro -> cerrar/reabrir -> biblioteca recuperada.
9. Probar dos cuentas, sesión expirada, logout y ausencia de cruce de datos.
No falta otra migración solo para almacenar el UID: V3 ya lo incorpora. Perfil/username y políticas adicionales sí requieren cambios de esquema según contrato.
Este informe no realizó la prueba real E2E ni creó usuarios Firebase/Neon.

Q. PLAN DE DESARROLLO PARA TERMINAR EL MVP
Orden por dependencias y valor comprobable; sin estimaciones arbitrarias de días.

BLOQUE 1: IDENTIDAD REAL Y USUARIO DE DOMINIO
Backend: aprovisionamiento idempotente por UID verificado, conflictos email y DTO mínimo; conservar denegación legacy.
Frontend: Firebase Core/Auth, Google Sign-In, login/registro/recuperación/logout, sesión observada, cliente Bearer/base URL.
Aceptación: cuenta nueva llega a /me 200; UID no lo elige cliente; email coincidente no secuestra cuenta legacy; dos cuentas aisladas.
No requiere rehacer V3.

BLOQUE 2: BIBLIOTECA Y PROGRESO REALES
Conectar UI existente a GET/POST/PATCH/DELETE /api/me/library.
Mapear status/format y null/0; no persistir porcentaje como sustituto de página canónica.
Añadir datos/fechas estrictamente necesarios para progreso e historial.
Aceptación: añadir, avanzar, editar formato, cerrar/reabrir y eliminar conserva coherencia; falla de red no muestra éxito falso; otra cuenta no ve ni modifica.
Es el bloque con mayor reutilización inmediata.

BLOQUE 3: CATÁLOGO GOOGLE BOOKS Y LIBRO UNIFICADO
Ampliar books/autores y cliente de búsqueda/importación; conectar búsqueda/detalle.
Aceptar metadata parcial, español y proveedor externo estable; deduplicación.
Aceptación: buscar título/autor/ISBN, añadir referencia a biblioteca, reiniciar y conservar; no guardar contenido externo completo.

BLOQUE 4: PERFIL/CONFIGURACIÓN + LISTAS/FAVORITOS/RESEÑAS
Agregar perfiles y configuración, endpoints propios y anonimato correcto.
Subida avatar/portada reutilizable con Cloudinary.
Conectar formularios existentes y eliminar datos iniciales ficticios de la experiencia real.
Aceptación: cambios reaparecen tras login, reseña anónima no expone autor interno, no se edita recurso ajeno.

BLOQUE 5: AUTOPUBLICACIÓN Y CAPÍTULOS
Libro CAPITULO_0 con creador, borrador/publicado y capítulos secuenciales.
Sustituir WriterLocalService como fuente autoritativa por repositorio API.
Definir tratamiento de borradores locales existentes: nunca importarlos silenciosamente a otra cuenta.
Aceptación: autor crea/edita/publica; otro usuario solo lee lo publicado; no modifica obra ajena; portada externa y orden coherentes.

BLOQUE 6: SOCIAL, PRIVACIDAD Y COMUNIDAD
Seguir/solicitudes/bloqueos; aplicar privacidad en consultas.
Comentarios/respuestas/likes; reportes con integridad y moderación por dueño/rol según operación.
Aceptación: perfil privado requiere aceptación; bloquear afecta operaciones; único like; comentarios ocultos no desaparecen físicamente; no se ocultan reseñas por decisión del autor; reportes persistentes.

BLOQUE 7: PUNTOS LECTORES
Cargar datos curados por equipo, API de consulta y fotos; conectar mapa actual.
Aceptación: marcadores/ficha salen de DB, datos no ficticios, secretos fuera de fuentes; comprobar Android real.
No crear plataforma de alta pública de lugares si el alcance no la pide.

BLOQUE 8: CIERRE TÉCNICO Y VALIDACIÓN DEL MUST
Pruebas aisladas PostgreSQL en entorno autorizado, smoke Firebase real, integración app/API, CI, contratos documentados, CORS web explícito, HTTPS/despliegue y limpieza selectiva de mocks.
La autorización para probar local no autoriza migrar Neon compartido.

BLOQUE 9: SHOULD HAVE
ML Kit ISBN (reutiliza búsqueda real), Gemini, clubes/membresías/encuentros curados, retos y mood.
Insignias después, según alcance Could Have.
No bloquear el primer MVP integrado por mejoras opcionales.
