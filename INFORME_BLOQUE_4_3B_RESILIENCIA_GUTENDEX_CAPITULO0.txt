2. DIAGNÓSTICO FOCALIZADO
El repositorio HTTP mantiene un timeout de 15 segundos, parámetros search/languages y validación estricta de páginas HTTPS del mismo proveedor y consulta. Se conserva sin cambios.
4.3A ya evitaba solicitudes idénticas simultáneas, descartaba respuestas obsoletas por generación, conservaba datos de la misma consulta durante actualización/fallo y mantenía caché de páginas por búsqueda, idioma y URI.
La limitación principal era el ciclo de vida: caché de tres minutos eliminada al cerrar el catálogo. Una nueva apertura dependía otra vez de una respuesta remota, aunque se hubieran consultado datos válidos previamente.
Había varios avisos separados para resultados guardados y error de actualización. La portada tenía un respaldo básico solo ante ausencia/error y una alternativa de carga HTML en Web, pero no recordaba explícitamente el fallo durante reconstrucciones del mismo widget.
HTTP 522/503, latencia del servidor y restricciones CORS no quedan resueltos por esta corrección Flutter. No se midió ni se certificó una mejora de latencia del servidor público.

3. SOLUCIÓN Y ESTADOS
Se reutiliza el caché de sesión 4.3A y se añade un almacén local pequeño, exclusivamente de metadatos públicos recibidos correctamente.
Al abrir una consulta sin resultados visibles se comprueba su copia local exacta. Si es válida se muestra sin lanzar una solicitud HTTP automática. La pantalla indica que procede de una consulta anterior, con máximo de 24 horas, y ofrece Buscar para actualizar.
Buscar/Enter/Reintentar fuerzan una actualización explícita, salvo que ya exista la misma solicitud en curso. Los resultados correspondientes a esa consulta permanecen visibles durante carga y ante timeout/error. Un éxito sustituye los datos y elimina el estado de copia guardada.
Búsqueda o idioma distintos reinician el contexto; nunca se usan datos de otra clave para rellenar una consulta sin resultados. La recuperación local también respeta la generación actual.
Carga inicial: indicador existente y texto legible sobre la espera del servicio público. Actualización: indicador lineal con resultados anteriores. Error: un único contenedor con el mensaje controlado y una explicación secundaria, junto a Reintentar catálogo. No se acumulan los avisos de error y de caché.
Una respuesta vacía exitosa sigue siendo distinta de un fallo. No hay temporizadores de reintento automático ni ciclos de solicitudes.
La lectura local tiene un límite independiente de 500 ms: si el almacenamiento no responde, continúa la solicitud normal de red. Una lectura local que termine después no puede sobrescribir resultados nuevos. Este límite NO cambia el timeout HTTP de 15 segundos.

4. CACHÉ Y LÍMITES
Sesión, sin modificar gutendex_page_cache.dart:
- Clave exacta: búsqueda con trim, idioma y URI de página.
- TTL de tres minutos, máximo ocho páginas, 256 libros y 500.000 unidades de texto.
- Evicción LRU y eliminación al cerrar el controlador.
- Conserva páginas consultadas, aislamiento, deduplicación y protección frente a paginación obsoleta.

Persistencia añadida con shared_preferences 2.5.6 ya presente en el proyecto:
- Clave propia: gutendex.public_catalog.v1; esquema versionado.
- Máximo 60 libros en total, cuatro primeras páginas de consultas y 250.000 unidades UTF-16 del JSON serializado, incluida su estructura. Equivale como máximo a unos 500 KB de unidades UTF-16, sin contar sobrecargas internas del runtime.
- Son máximos simultáneos: con páginas grandes caben menos de cuatro consultas. No se promete conservar todas las búsquedas; se evictan las más antiguas guardadas.
- Se conserva la primera página completa, no un recorte que pudiera saltar libros al paginar. Una página demasiado grande no se guarda.
- Se contabiliza texto antes de serializar y se verifica el tamaño final. Las escrituras de cada instancia se serializan.
- Fecha UTC de obtención y caducidad de 24 horas; leer no renueva la fecha. Se rechazan fechas futuras y entradas caducadas al recuperar.
- Se validan versión, tamaño, claves, idiomas admitidos, cantidad de entradas/libros, identidad de libros, cuenta y enlaces next de la misma búsqueda/idioma y host HTTPS. Datos dañados o incompatibles no se muestran.
- Solo campos públicos: título, autores/traductores, idiomas, materias, sinopsis original, formatos/URLs, copyright, descargas y datos de página. Sin tokens, identidad de usuario, credenciales ni datos de Biblioteca.
- No se guardan imágenes, novelas, archivos TXT, contenido de lectura ni páginas adicionales en disco.
- Fallos de preferencias no convierten un éxito HTTP en error ni borran resultados visibles. No se llama a clear ni se alteran claves ajenas.
- Es un guardado de mejor esfuerzo: permisos del navegador, limpieza de datos, modo privado y disponibilidad del almacenamiento pueden impedir conservarlo. No es un respaldo garantizado.
La lista visible que el usuario acumula con Más obras conserva el comportamiento anterior; los límites anteriores corresponden a los almacenes de caché.

Documentación oficial consultada para la dependencia ya instalada:
https://pub.dev/packages/shared_preferences

5. PORTADAS
GutendexCover ahora conserva estado de fallo para la URL actual. Muestra un respaldo de crema/café/dorado con icono literario durante la espera, cuando falta una URL o cuando falla la imagen. Incluye semántica accesible y admite título real cuando el tamaño permite mostrarlo.
No se programan reintentos. Reconstruir el mismo widget tras un fallo no vuelve a crear Image.network. Una URL distinta permite un nuevo intento. Destruir y volver a crear la pantalla puede permitir otro intento normal; no se promete una lista persistente de imágenes fallidas.
Se retira la alternativa HTML de carga Web de este widget: un fallo utiliza el respaldo local, sin añadir otro mecanismo de acceso. No se intenta eludir CORS ni se modifica seguridad del navegador.
Se mantienen imágenes reales cuando cargan correctamente. No se modifican portadas de Google Books ni componentes compartidos. La ficha utiliza el mismo widget existente sin cambios propios de código.

8. QUÉ FUNCIONA SIN CONEXIÓN Y QUÉ NO
Con la aplicación ya cargada, almacenamiento disponible y una copia válida de esa búsqueda/idioma, el catálogo puede recuperar la primera página de metadatos consultados y abrir una ficha con esos datos. La ficha conserva la información inicial aunque falle su actualización remota.
El lector/importador TXT mantiene su funcionamiento local anterior. No se guardó ni subió el archivo del usuario y no se modificó el lector.
No hay catálogo offline completo, imágenes persistentes ni texto completo descargado. Las consultas no guardadas, páginas adicionales no disponibles en sesión, actualizaciones de ficha, enlaces externos e imágenes necesitan internet.
No se garantiza iniciar toda la aplicación sin red ni que autenticación y recursos de arranque estén disponibles offline. Tampoco se garantiza recuperación tras borrar almacenamiento, cambiar de navegador/origen o caducar/evictarse la entrada.
El transporte HTTP previo no se reconstruyó: generaciones descartan respuestas obsoletas, pero no se afirma cancelación física de todas las solicitudes anteriores. Cerrar el catálogo conserva el cierre del cliente existente.
No se implementaron proxy, descarga directa, scraping, traducción ni modo demostración con obras ficticias.
